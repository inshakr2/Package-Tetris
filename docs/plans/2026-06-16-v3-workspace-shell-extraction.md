# 2026-06-16 V3 워크스페이스 구조 분해 1차 계획

## 목적

V3는 현장 사용자가 쓰는 흐름을 유지하면서, 7,000줄 이상으로 커진 `tetris-workspace-app.tsx`를 점진적으로 분리한다. 첫 증분은 화면 동작을 바꾸지 않고 leaf UI부터 분리해 이후 작업본 문서 모델, QA 자동화, 시뮬레이션 패널 확장을 안전하게 받을 수 있는 구조를 만든다.

## 역할별 검토

- product-manager: V3 첫 개발 증분은 큰 화면 개편보다 구조 안정화가 우선이다. 사용 흐름과 문구를 그대로 유지한 채, 작은 단위로 분리하고 검증한다.
- business-analyst: 현장 작업자는 기존 1~4번 흐름을 계속 테스트해야 하므로 사용자 행동 변화가 없는 작업부터 적용한다.
- ui-designer: 이번 증분은 UI 배치와 시각 계층을 변경하지 않는다. 컴포넌트 경계만 분리해 추후 화면 단위 개선의 기준을 만든다.
- ui-ux-tester: 표시 결과가 동일해야 하며, 구조 변경 후에도 360px~1280px 검증 기준을 유지한다. 시각 변경이 생기는 증분부터 브라우저 스크린샷 검증을 필수로 붙인다.
- nextjs-developer: `선택된 공간` 요약처럼 의존성이 낮은 leaf 컴포넌트와 치수 포맷 유틸부터 분리한다.
- code-reviewer: 문서상 완료와 실제 구현이 어긋나지 않도록 구조 회귀 테스트를 추가한다.

## 검토한 접근

1. 전체 워크스페이스를 한 번에 섹션별로 재작성한다.
   - 장점: 최종 구조가 빠르게 보인다.
   - 단점: 현장 시연 중인 UI 회귀 위험이 크고, 원인 추적이 어렵다.

2. 문서와 테스트만 보강하고 코드 분리는 뒤로 미룬다.
   - 장점: 위험이 낮다.
   - 단점: V3 구조 개선이 실제 코드에 반영되지 않아 이전의 문서/구현 불일치 문제가 반복될 수 있다.

3. leaf 컴포넌트부터 실제 분리하고, 구조 테스트로 고정한다.
   - 장점: 사용자 화면 변경 없이 구조 개선을 시작할 수 있고, 이후 분리 기준을 만든다.
   - 선택: 이번 증분에 적용한다.

## 이번 증분 범위

- `formatDimensions`를 공통 유틸로 분리한다.
- `SelectedSpaceSummary`를 별도 컴포넌트로 분리한다.
- `SpaceLibraryPanel`을 별도 컴포넌트로 분리해 1번 섹션 책임을 워크스페이스 앱 본문에서 덜어낸다.
- `BlockLibraryPanel`을 별도 컴포넌트로 분리해 2번 섹션의 저장 박스 조회, 엑셀 포맷, 일괄등록 모달 책임을 워크스페이스 앱 본문에서 덜어낸다.
- `createTopBlockGroups`, `createChildBlockGroups` 그룹 옵션 로직을 공통 유틸로 분리해 박스 등록/조회/추가 시뮬레이션이 같은 그룹 기준을 사용하게 한다.
- `tetris-workspace-app.tsx`가 분리된 컴포넌트를 import하도록 변경한다.
- 구조 테스트로 “문서에만 완료처럼 보이는 상태”를 방지한다.
